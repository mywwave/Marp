# Эталоны (референсы) Marp

Эталон — кликабельная HTML-страница `docs/design/<раздел>.html`, по которой потом верстают продукт 1 в 1. Он показывает **каждый экран, состояние, окно и текст** раздела на реалистичных данных, в светлой и тёмной теме и в узком окне. Это спецификация, а не картинка: агент, который будет реализовывать, не должен ничего додумывать.

Перед работой загрузите `.agents/skills/marp-design-system/SKILL.md` и его `references/`. Все законы дизайн-системы действуют внутри эталона так же, как в продукте.

## 1. Определите режим

| Режим                   | Когда                                                             | Что делать с файлом                                                                                                    |
| ----------------------- | ----------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| **A. Новый**            | `docs/design/<раздел>.html` не существует                         | Создать с нуля                                                                                                         |
| **B. Полный пересмотр** | Эталон есть, но просят «новый», «с нуля», «пересмотрим полностью» | Старый → `docs/design/archive/<раздел>-YYYY-MM-DD.html` (пути `assets/` → `../assets/`), новый пишется с чистого листа |
| **C. Точечная правка**  | Названы конкретный экран, блок, состояние или окно                | Править только это; обновить инвентаризацию и чек-лист по затронутым пунктам                                           |

Если режим неясен (эталон есть, просьба «сделай эталон X»), спросите один раз: «пересмотреть полностью или поправить <что>?». Остальное не спрашивайте, если отвечает код. Продуктовые развилки не блокируют работу: выберите разумный вариант и вынесите в «Открытые вопросы».

В режимах A и B думайте как продуктовый дизайнер: зачем раздел, что пользователь делает в нём сотни раз в день, на какие три вопроса он отвечает, что лишнее, где тупики. Не переносите текущую структуру Marp по инерции — но ни одна функция не должна потеряться молча.

## 2. Сначала инвентаризация (A и B; в C — дополнить)

Файл `docs/design/inventory/<раздел>.md` — что продукт умеет сейчас, собранное по коду:

- web: роуты `apps/web/src/routes/`, компоненты `apps/web/src/components/**` (включая `*.logic.ts`), все строки интерфейса, тосты, модалки, пустые состояния, скелетоны, ошибки, клавиши (`keybindings`), пункты палитры команд (`CommandPalette*`);
- desktop: `apps/desktop` — меню окна, IPC-действия, нативные диалоги, полоса заголовка;
- контракты `packages/contracts` — поля, статусы, варианты;
- сервер `apps/server` — что происходит молча (чекпоинты, переподключение, очередь), ошибки, которые доходят до UI;
- провайдеры — чем раздел отличается у Codex, Claude, Cursor, Grok, OpenCode, Antigravity;
- права (`CLIENT_GUARDED_RPC_SCOPES`, гость, удалённый клиент), режимы соединения (локально, удалённо, туннель).

Формат:

```
# Раздел «X» — инвентаризация
Источник правды для эталона `docs/design/x.html` (прошлый — `archive/x-YYYY-MM-DD.html`).
**Что это за раздел.** 2–4 предложения.
**Как читать строку.** `- **ID** что есть — `файл:строка` ⟶ статус`. Статус: `✓ #экран` (в скобках — что поменяли), `＋ новое: что`, `✗ убрано: почему и как сделать то же самое`.
## A. Вход, адреса, клавиши
- **A-01** … — `apps/web/src/routes/...:12` ⟶ ✓ #main
## B. …
```

Пункт без статуса = недоделанный эталон. `✗ убрано` — только с причиной и альтернативой.

## 3. Файл эталона

- Подключить общее: `<link rel="stylesheet" href="assets/reference.css">` и `<script src="assets/reference.js"></script>` (тема, акцент, поповеры, модалки, тосты, вкладки экранов, демо-панель, `?frame=1`, `Ref.$ / Ref.$$`, `Ref.icon()`). В `<style>` страницы — только то, чего нет в `reference.css`, и только через токены (`var(--space-*)`, `--ink-*`, `--surface*`, `--radius-*`, `--text-*`, `--dur-*`).
- Шапка документа: `.doc-nav` (собирается из `DOC_PAGES` в `reference.js` — новый файл добавить туда), переключатели темы и акцента, бейдж «Эталон · <Раздел> · <дата>», `h1`, `lead`: что за раздел, ссылка на инвентаризацию и архивную версию.
- Вкладки экранов `nav.screens` с `data-screen`; `#экран` в адресе открывает экран. Типовой набор: главный экран, первый запуск, рабочие состояния, вспомогательные экраны, **«Narrow»** (окно 720 / мобильный веб 390), **«Dialogs»** (каждое окно, подтверждение, меню открытыми), **«Checklist»** (инвентаризация со статусами).
- Экран продукта рисуется внутри `.app` (шелл: сайдбар + лист + панель) в масштабе 1:1, ширина рамки 1440 × 900 по умолчанию.
- Под каждым экраном — короткий `.screen-doc`: что видит пользователь, `doc-note` с решениями («почему так»).
- **Демо-панель** `.demo-bar` переключает состояния прямо на экране: провайдер (Codex / Claude / Cursor / Grok / OpenCode / Antigravity), статус агента (working / needs-you / done / failed / idle), загрузка, ошибка блока, пусто, много данных (100+ тредов, 50+ шагов), окружение офлайн, удалённый клиент / гость, desktop macOS / Windows / web.
- `?frame=1` прячет документацию и оставляет чистый экран — для скриншотов и сравнения с реализацией. `?frame=1#экран` открывает экран.
- Внизу: «Решения» (было → стало → почему), **«Нужно от сервера»** (чего нет в контрактах; в UI помечено `.be-tag` «needs server»), **«Открытые вопросы»**.
- Данные реалистичные: настоящие названия репозиториев, веток, файлов, команд, моделей провайдеров, правдоподобные диффы и выводы. «Сейчас» эталона зафиксировано в комментарии. Никакого lorem ipsum, «Test thread», «foo.ts».

## 4. Что соблюдать при проектировании

1. **Дизайн-система 1 в 1** — семь законов `marp-design-system`. Ближайший образец — в `reference.html` и соседних эталонах; не изобретайте новый вид кнопки, строки, карточки.
2. **Только реализуемые компоненты.** Каждый блок должен ложиться на примитив `apps/web/src/components/ui/*` или на компонент фичи. Новый общий компонент — явно в «Решениях» с описанием, где ещё пригодится.
3. **Консистентность между эталонами.** Те же шапки, строки, пустые состояния, окна и тексты, что в соседних разделах. «Везде по-разному» — дефект.
4. **Все поверхности** (`AGENTS.md` «Hit every surface»): web и desktop, точки входа (кнопка, меню, палитра, клавиша), каждый провайдер, удалённое окружение и обрыв связи, обратные состояния (archive → unarchive, snooze → unsnooze).
5. **Статус честный** — каждое семейство статусов показано там, где его видно; никаких бесконечных анимаций.
6. **Длинные списки** — проверить на 100+ строках по таблице `patterns.md`.
7. **Без тупиков** — из любого состояния есть путь дальше; первый запуск ведёт до первого ответа агента.
8. **Без лишнего.** Каждый экран отвечает: что происходит, нужен ли я, что дальше. Повтор одного факта в трёх местах, декоративные бейджи — убрать.
9. **Тексты** — по `references/copy.md`, финальные, на английском: их перенесут в код как есть.
10. **Адаптив и темы** — каждый экран в светлой и тёмной теме, с двумя акцентами и в узком окне; ни одного горизонтального скролла страницы.

## 5. Проверка перед сдачей

1. `python -m http.server 8765` в `docs/design/` (запущен в фоне, PID записан), открыть страницу.
2. Скриншоты Playwright `?frame=1#экран` каждого экрана: 1920×1080, 1440×900, 1024×768, 390×844; светлая и тёмная. Смотреть глазами: обрезки, налезания, пустоты, выравнивание, контраст в тёмной теме.
3. В консоли ноль ошибок; все вкладки, демо-переключатели, поповеры и окна открываются; `#экран` работает.
4. Каждый пункт инвентаризации имеет статус; «Checklist» рендерится без пропусков.
5. Пройти `marp-design-system/references/checklist.md`.
6. Скриншоты — в `docs/design/.output/<раздел>/` (gitignored), сервер остановить по записанному PID.

## 5а. Ни одна функция не пропадает

- Каждая функция, действие, состояние, клавиша, пункт меню и палитры, окно, текст ошибки и право есть в инвентаризации с `файл:строка` и получает статус.
- Всё интерактивное в эталоне работает в браузере: кнопки, меню, окна, раскрытие вызовов инструментов, поля, демо-переключатели. Статичная картинка вместо работающего элемента — дефект.
- **Независимая проверка.** После сдачи отдельный агент (не автор) сверяет инвентаризацию с экранами и с реальным кодом, прокликивает всё, снимает скриншоты. Находки — список «пункт → что не так»; исправлять, пока список не пуст.

## 6. Сдача

- Коммит только своих файлов (`git commit --only <пути>`): эталон, архив, инвентаризация, `assets/*` если меняли. Conventional commit: `docs(design): …`. Не пушить без просьбы.
- **Эталон ≠ реализация.** Продукт не трогать, пока пользователь не попросит реализовать.
- Отчёт коротко: режим, экраны, главные решения (было → стало), что нужно от сервера, открытые вопросы — списком.

## 7. Реализация по эталону (когда попросят)

- Сначала токены: перенести значения из `docs/design/assets/reference.css` в `apps/web/src/index.css` по словарю `tokens.md`, затем примитивы `components/ui`, затем фичи.
- Инвентаризация = чек-лист работ: каждый `✓`/`＋` реализован, `✗` удалён.
- Вёрстка сверяется скриншотами `?frame=1#экран` против продукта на тех же размерах и темах, на данных той же формы (`vp run dev` с засеянной базой, провайдер `Replay (dev)`). Итерировать, пока не совпадёт.
- Расхождение без API — в «Нужно от сервера» и пользователю, а не молча упростить.
- Каждый перенесённый экран — проверка в реальном клиенте (`test-marp-app`), `vp run check:changed`.
